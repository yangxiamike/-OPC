# 公司治理策略 v0.1

日期：2026-05-17
状态：当前协作约定
适用范围：一人公司 OPC 内部治理

## 1. 定位

本文件是内部协作策略，不是固定制度，也不是对外材料。

核心目的：

> 让董事会、托特秘书/Codex、Hermes CEO Agent、Kanban 和项目库各司其职，避免愿望过大、任务越级和治理过重。

## 2. 基本链路

当前协作链路：

> 愿望 -> 尺度审计 -> 董事会决议 -> 必要时形成 CEO 任务输入 -> CEO 拆解 -> Kanban 执行 -> 项目库复盘。

基础制度与经营团队搭建链路：

> 愿望 -> 尺度审计 -> 董事会决议 -> 董秘承办单 -> 托特秘书搭建 -> 董事会验收 -> CEO 试运行反馈。

一句话规则：

> 王座定方向，CEO 拆军令，Kanban 管执行。

补充规则：

> CEO 未到位前，不把基础制度和团队结构建设交给 CEO；由托特秘书承办到可试运行状态。

## 3. 愿望尺度审计

夏董提出愿望后，Codex 先判断尺度，再决定输出形式。

| 层级 | 处理方式 |
| --- | --- |
| 愿望级 | 只整理方向、风险、取舍和可验证问题 |
| 战役级 | 形成董事会决议；涉及经营执行时形成 CEO 任务输入，涉及基础制度或团队搭建时形成董秘承办单 |
| 项目级 | 生成项目目标、边界、验收口径，交给 CEO 拆解 |
| 任务级 | 直接执行或整理为单个明确任务 |

尺度过大的信号：

- CEO 任务输入超过 3-5 个核心要求。
- 需要同时启动市场、设计、开发、获客、系统等多条线。
- 存在大量未知判断，却已经开始写具体任务。
- 还没验证客户意向，就开始规划系统、流程、团队和长期资产。
- 董事会文件开始像 Kanban。

压缩方法：

> 大愿望 -> 阶段目标 -> 可验证问题 -> CEO 任务输入。

## 4. 角色边界

董事会负责：

- 定方向
- 定阶段目标
- 定边界
- 批准初始执行团队结构
- 批准重大取舍
- 复盘关键结果

董事会不负责：

- 拆细任务
- 预设市场分类
- 预设设计风格
- 预设执行节奏
- 管 Kanban

Hermes CEO Agent 负责：

- 接收董事会目标
- 拆解执行方案
- 建立 Kanban
- 调度各 Agent
- 跟踪进度和风险
- 在授权团队结构内安排执行
- 提交需要董事会拍板的问题

初始执行团队结构由董事会批准；日常分工、任务调度和 Kanban 由 CEO Agent 决定。若需新增、取消或重组核心 Agent 角色，CEO Agent 应提交理由，由董事会确认。

托特秘书/Codex 负责：

- 做愿望尺度审计
- 起草董事会决议、董秘承办单和 CEO 任务输入
- 在 CEO 未到位前，承办基础制度与 Hermes 经营团队结构搭建
- 审计 Hermes 输出
- 维护文件结构、项目库和关键规则
- 提醒越界、过度承诺和复杂化风险

OA 系统、Hermes Agent 系统、Holographic Memory 与 Hermes 经营团队结构等王座层基础制度，由董事长与托特秘书/Codex 审议确立。Hermes CEO Agent 可参与试运行和反馈，但不拥有最终定义权。

## 5. 文件边界

董事会决议：

- 记录方向、目标、边界、授权和验收口径。
- 不写具体任务清单。
- 使用决议编号作为文件主键。

CEO 任务输入：

- 把董事会目标交给 CEO Agent。
- 对基础制度类事项，只交付试运行边界和反馈要求，不授予 CEO 制度定义权。
- 不替 CEO 预设详细拆解、风格分类、日程节奏。
- 不要求 CEO 向董事会提交内部 Kanban 或任务分配细节。
- 跟随对应董事会决议编号命名。

董秘承办单：

- 承接基础制度、组织骨架、OA、Memory、团队结构等王座层事项。
- 在 CEO 尚未到位时，作为当前执行入口。
- 写清目标、边界、交付物和移交条件。
- 不替未来 CEO 预设内部 Kanban 和日常排期。

Kanban：

- 承载具体任务、责任 Agent、状态和卡点。
- 由 CEO Agent 管理。

项目库：

- 保存项目档案、交付物索引和复盘。
- 不负责指挥任务。

等夏董拍板：

- 只放“还没决定、需要夏董一句话”的事。
- 每份文件开头必须写清楚：夏董要拍什么板、托特建议选什么、拍板后我去做什么。
- 不把这类内容写进配置、守则、SOUL 模板正文，避免把“候选想法”误读成“已经算数的规则”。
- 夏董拍板后，再把确定内容放回对应正式文件；没拍板的继续留在这里。
## 6. 档案命名规则

日期文件用于连续记录，编号文件用于正式决议和对应交接，固定文件用于长期生效规则和经验资产。

当前规则：

- 每日复盘使用日期命名。
- 董事会决议使用编号命名，例如 `第001号_一人公司集团运行系统_v0.1.md`。
- 董秘承办单跟随决议编号命名，例如 `董秘承办_第001号_一人公司集团运行系统_v0.1.md`。
- CEO 任务输入跟随决议编号命名，例如 `CEO输入_第001号_一人公司集团运行系统_v0.1.md`。
- 等夏董拍板使用日期命名，例如 `2026-05-18_OPC_启动与复盘_请夏董拍板.md`。
- 公司治理策略、执行团队交付要求、董事会经验、通用工作经验等活文档使用固定文件名，不在文件名中加入日期或编号。

## 7. 经验与权限隔离

董事会级经验只服务方向、授权、边界、风险和重大取舍判断，不默认下发执行团队。

执行团队交付要求属于公司治理规则，可以进入 CEO 任务输入，作为 Hermes CEO Agent 和各执行 Agent 的执行约束。

项目经验只随对应项目上下文读取，避免把局部案例升级成全公司规则。

通用经验沉淀统一放入 05_经验沉淀，治理文件不承载经验库职能。

## 8. Token 成本治理

公司运转高度关注 token 成本，所有沉淀和交付都要优先短、准、可执行。
- 中文 Markdown 文件统一使用 UTF-8（带 BOM）编码保存，避免跨工具乱码与重复沟通成本。
- 多工具协作的文档在批量改动前先统一行尾策略（LF 或 CRLF）并保持仓库一致，避免仅行尾变化造成虚假 diff 与审计噪音。
- 接入真实外部系统标识的配置、日志和运行记录在推送远端仓库前，必须先做公开边界与脱敏判断。

## 9. 自动化运行纪律

- 日终收尾自动化按登记时间串行执行；若直接触发会争抢状态库或卡住，则在当前会话按原配置顺序执行并留痕。
- 飞书是前台 OA、摘要索引和通知中枢，不是公司事实源；凡涉及正式制度、客户事实、项目交付和复盘定案，仍以 OPC 本地文件为准。
- 飞书自动化先做摘要通知、状态同步和风险升级，不先做复杂审批流；任何 webhook URL、secret、token、cookie、私钥和客户隐私不得写入 OPC 或飞书多维表格。
- 飞书消息进入 Hermes 或 Memory 前必须经过路由判断：普通状态进执行室，文件变化进文件通知，报价、收付款、客户承诺、延期、范围变更、声誉风险和密钥问题升级到董事会 / 董秘处。
- 凡需夏董拍板的事项统一使用可点击的决策卡片并在点击后回写结果，不再用纯文本 A/B 作为正式拍板动作。
- 托特董秘 Hermes 可以承办 OPC 内部飞书工作群的创建与成员拉入，但默认只限内部协作场景；涉及客户群、外部协作者群或外部成员拉群，仍需夏董拍板。
- 飞书群管理能力通过 `04_公司治理策略/manage_feishu_group_v0.1.ps1` 执行，凭据只从托特 profile 本地 `.env` 读取，不回写 OPC；每次动作都要落入 `02_董秘承办单/feishu_group_audit.md`。
- 正式主线切换后，旧轮询、旧路由、旧脚本等过渡方案只保留历史追溯用途，并在原文件显式标明废弃且停止继续扩展。

## 10. 修订原则

本策略可以随 Hermes、飞书、Kanban 或项目库变化而修订。

修订原则：

> 只保留能约束行为、提升效率、降低风险的规则；不要为了治理而治理。
