# 飞书机器人配置工作流

日期：2026-05-18
状态：可复用
适用范围：OPC 内部 Feishu / Lark 机器人新增能力、补权限、真实验收

## 定义

飞书机器人配置完成，必须同时满足四项：

1. 本地调用入口已配置。
2. 对应身份所需 scope 已开通。
3. 真实 API 已验收成功。
4. 人工授权步骤已完成。

缺任一项，都不算完成。

## 身份拆分

处理飞书机器人时，必须先分清两类身份：

1. 应用身份：bot / tenant 级动作。
2. 用户身份：user OAuth 级动作。

两类身份的 scope 互不替代，必须分别检查。

## 标准流程

1. 先定义目标动作。
   只写动作，不写泛化目标。例如：`建群`、`拉人进群`、`发消息`、`传文件`。

2. 再列动作对应的最终生效条件。
   每个动作都要拆成：本地脚本、应用身份 scope、用户身份 scope、人工授权、真实 API 验收。

3. 先做权限预检，再做实现。
   不先写脚本再碰运气。先确认缺哪些 scope、缺哪类身份、是否需要人工确认。

4. 本地实现只负责调用，不负责假定平台可用。
   本地脚本、配置、审计、日志先配好，但不得把“脚本已写好”当成“平台已开通”。

5. 必须做真实 API 验收。
   每个目标动作至少打一次真实接口。只看文档、只看配置、只跑 dry-run，都不算验收。

6. 按动作分别下结论。
   不能把“建群成功”表述成“群管理权限已完成”。动作必须逐项给结论。

7. 一旦报错，直接回收到具体缺口。
   输出格式固定为：`哪个动作失败`、`失败代码`、`缺哪个 scope 或哪个人工步骤`。

8. 人工授权完成后，必须复验。
   用户点完授权页后，不直接宣布完成；要重新打真实接口，确认动作已生效。

## 常见动作与 scope

- 建群：
  应重点检查 `im:chat:create`。

- 拉人进群：
  应重点检查 `im:chat.members:write_only`。

- 群本身读写：
  应重点检查 `im:chat`。

- 仅管理员可拉人场景：
  额外检查 `im:chat:operate_as_owner`。

## 输出规则

处理结果只允许三种结论：

1. 已完成：真实动作成功。
2. 未完成：已定位到明确缺口。
3. 待人工授权后复验：当前只差人工确认。

禁止使用“基本好了”“应该可以”“差不多通了”这类模糊表述。

## 本次沉淀

这次验收得到的直接规则是：

- `建群成功` 不等于 `拉人进群成功`。
- 同一机器人能力，可能同时卡在应用身份和用户身份两条线上。
- 最后的平台授权页，如果需要人工确认，就必须明确标记为人工步骤，不能假装后台已完成。
